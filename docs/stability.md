# 单机版工程与稳定性收尾

本轮收尾面向单网关和本机 TiDB 部署，覆盖回归、发布、故障恢复和多会话同步。收尾完成后，同一版本能从干净环境安装、升级和验收。运行异常时能定位故障，恢复后能用原发送键和客户端同步进度继续操作。

`main` 的 `4081472` 已通过工作区检查、真实 TCP + TLS 和 TiDB 回归、网关进程重启及旧库离线升级。故障验收覆盖原库重新打开，数据库备份恢复仍需单独验收。[现有验收入口](./gateway.md#单机版本验收)

## 实施顺序

| 顺序 | 交付 | 验收 |
|---|---|---|
| 1 | 统一真实 TiDB 的冒烟、完整回归和发布预检 | 干净环境可重复运行，同一候选提交的结果可追溯 |
| 2 | 补齐启动、故障和排空的运行状态 | 计划停机和依赖中断都能定位，未决发送重连后可结算 |
| 3 | 演练备份恢复和离线升级交接 | 完整副本可以接管，落后的副本保持隔离 |
| 4 | 测量并优化多会话同步 | 大量空会话和长分页下，活跃业务仍能取得服务，所有会话最终补齐 |

前三项是单机版发布条件。多会话压测可与运行和恢复演练并行，调度改动按实际收益合入。

## 回归和发布

- 复用现有 Rust 锁定版本和测试夹具，提供一个验收入口。冒烟选择发送回执、末条漏推补齐及原库重启三个路径，完整回归覆盖现有存储、客户端和真实网关功能与故障用例。容量压测独立执行，便于控制机器和负载。
- 通过本地验收入口启动固定版本的 TiDB、TiKV 和 PD，验证 `tidb_version()`，沿用测试库前缀和显式写入开关。启动或验证失败时返回错误，运行结束后清理测试实例。涉及消息链路的改动先在本地跑相关用例，候选版本发布前运行完整回归。[本地验收命令](../CONTRIBUTING.md#checks)
- 记录候选提交、Rust 和 TiDB 版本、执行范围、失败用例和耗时。将退出码、网关日志和失败结果留在同一次记录里。失败时可在一次性环境复现。候选二进制和使用的配置格式、存储版本一起交付。
- 发布预检校验 TLS 与设备凭证、存储 ID、存储版本和数据库可连接性。启动检查失败应在对外接入前退出，并给出可操作的原因。恢复启动误用初始化模式或连接错误库的场景进入验收。[启动入口](../crates/iam-gateway/src/main.rs) · [现有验证入口](./storage.md#本机控制台与验证)

## 运行和计划停机

首批观测复用现有网关和存储边界，记录启动、排空和超时事件，以及活跃连接数、入口拒绝、回包与推送积压、TiDB 连接或事务失败、未决发送与同步重置次数。耗时沿用握手、认证、队列、事务和客户端落盘的分段口径。标签限制在命令、阶段和原因，日志排除凭证、票据、数据库连接串和正文。[分段计时](./gateway-perf.md#集中重连分段测量)

就绪状态依赖启动校验、监听状态和近期的 TiDB 探测。探测有超时、限频，走短只读查询且避开 `store_control` 行锁。依赖短暂抖动用连续失败阈值处理，进入排空立即撤下就绪状态。进程存活单独判断。是否需要管理端口由部署方式决定，先验证状态信号足以区分启动、可接入、依赖异常和排空。

收到 `SIGTERM` 后，先撤下就绪状态并停止新连接和请求准入，再等待已准入请求结算，尽力发送剩余应答。超过排空期限记录超时以及剩余在途数。原设备在结果查询窗口内用原发送键查询未确认的提交结果，收件端从已保存进度补齐。演练分别在 TiDB 提交前、提交成功但应答未到达时发出 `SIGTERM`，加一组 TiDB 中断和慢读连接，确认停机有上界、回执可结算、重启后无重复或序号缺口。[现有停机入口](../crates/iam-gateway/src/lib.rs)

## 数据库恢复和升级

原库重启沿用 `resume`。计划更换数据库时先隔离入口和所有旧写入方，等待在途写入确定结果，再记录冻结点。使用 TiDB 一致性快照恢复到隔离的目标库，备份覆盖 IAM 的控制记录、消息、拒绝记录和权限状态。恢复清单记录源库、目标库、存储 ID、存储版本、冻结点和备份位点，保存在恢复库之外。[TiDB 快照备份与恢复](https://docs.pingcap.com/tidb/stable/br-snapshot-guide/)

开放写入需要同时确认源库仍被隔离、目标库对应本次交接、恢复点覆盖冻结点，以及存储检查和恢复验收通过。部署入口据此放行目标库。旧备份即使带有相同存储 ID，也须在隔离环境核查。灾难下无法证明数据完整时，保持业务写入口关闭，记录可恢复点、缺失范围和实际恢复耗时。旧游标、票据和未决发送应一并纳入恢复判断。[存储恢复规则](./storage.md#恢复与同步)

演练使用真实备份恢复到新库，准备带成功回执、已持久化拒绝和未决结果的发送键。覆盖冻结后完整副本与丢掉尾部提交的旧副本。完整副本上验证同键回执一致、历史和权限可读、原 SQLite 游标能续读。旧副本上验证部署入口拒绝开放写入。离线升级另测中断后重跑，旧二进制仅在对升级后存储的兼容性经过验证时回退。

历史物理清理在恢复演练和保留规则确定后再做。当前成功消息行同时保存正文、去重和回执依据。届时先验证可见历史下界、结果查询截止、关闭水位和已有分页的衔接，再决定如何删除正文又保留需查询的发送结果。[发送事务](./storage.md#发送事务)

## 多会话同步

当前客户端先同步账户，再串行扫描全部已知会话，单轮会话同步可连续取完多页。新增的在线命令和持久队列发送共用这条连接。少量活跃会话叠加大量空会话时，空 `SYNC` 会放大请求数，长分页也会拉长前台操作等待。[当前同步实现](../crates/iam-client/src/sync.rs)

先从少量会话到 100 和 500 个会话建立对照，每档保留少量活跃会话，分别测试持续在线、断线重连和长期离线。记录每设备 `SYNC` 次数、发送和在线命令 P99、最后一台设备补齐时间、超时和未发出请求数。基线与候选在相同环境下交替复跑，同时检查原有纯发送和 32、64 台集中重连基线。[现有容量对照](./gateway-perf.md)

优先把增量同步切成有界的页批次，让发件队列、在线命令和心跳能在页间运行。账户变更先应用，受影响的会话重新检查访问范围。普通推送可提高对应会话优先级，所有会话仍需周期核对。每页原子保存变更和进度，掉线或分页凭证到期从已落盘进度续读。快照保持完整后再切换本地基线，另测多页快照峰值内存，再决定是否增加暂存。

优化验收以真实 TiDB 和 TCP + TLS 为准。多会话负载下前台等待应可重复下降，原有负载的发送尾延迟、补齐时间和失败率应在基线波动范围内。末条漏推、重连、分页凭证到期和撤权过程中核对消息及进度，避免通过缩小同步范围换取速度。
