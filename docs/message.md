# 消息可靠性设计

服务端在 TiDB 提交后确认发送成功，并尝试向在线设备推送。接收设备即使离线，上线后也可以通过同步补齐仍保留且有权读取的消息。

## 一条消息怎么走

### 上行：确认消息存好了

| 字段 | 用途 |
|---|---|
| `client_msg_id` | 客户端首次发送前生成的 UUIDv7，标识这条消息。查询和重发都沿用原值 |
| `req_id` | 关联一次请求和响应。同一连接内严格递增，每次查询或重发都用新的请求号 |
| `create_seq` | 服务端提交时分配的会话序号，决定消息在会话里的顺序 |

UUIDv7 可以由设备自行生成，重连后仍可用同一个 ID 指向原消息。ID 里的时间用于判断还能否首次提交、还能否查询原结果。会话顺序由 `create_seq` 决定，`client_msg_id` 无需连续递增。

**服务端已实现。** TiDB 按租户、用户、设备、会话和 `client_msg_id` 去重。首次发送通过校验后，在同一个事务里分配 `create_seq`，保存消息和重建回执所需的信息，提交后才返回 `committed`。查询期限内，如果已经记录发送结果，同键同正文返回原结果，同键换正文返回冲突。服务端目前只在当前连接内检查同一会话是否还有未决发送。

**客户端已实现持久队列。** `iam-client` 用 SQLite 保存消息键和正文，再按会话串行发送。假设 A 的回执丢了，设备重连或重启后先用同一身份和原键查 `SEND_STATUS`。服务端允许重发时，仍用原键和原正文。超时或结果暂不可用时，A 继续待确认。只有保存了 A 的最终结果，或服务端确认 A 已不能再提交（`acceptance_closed = true`），才发送 B。后一种情况下，A 的结果仍可能未知。真实 TiDB 验收覆盖了提交前中断、提交后丢回执和客户端重开本地库。

### 转发：提交后再推给在线设备

**服务端已实现。** 首次发送提交成功后，服务端把新消息和会话序号编码成 `PUSH`，为本实例内有权限的在线连接生成推送帧，跳过发出请求的连接。当前只生成帧，由调用方负责投递。查询期限内，用原键和原正文重发已提交的消息时，服务端返回原回执，不重新生成推送。

服务在提交后、推送前崩溃，或者推送丢失时，只要游标仍有效，接收设备就用最后保存的游标发起 `SYNC`。服务端从同一份 TiDB 消息表按会话序号读出游标之后的消息，设备再把补回的消息和新游标一起保存。真实 TiDB 验收已在提交成功、推送尚未生成时终止服务进程，并确认重启后发件端查回的回执与收件端补到的消息一致。

### 下行：消息和游标一起保存

账户同步从 TiDB 的账户变化记录发现新增会话、撤权和重新授权。首条推送丢失时，定时账户同步仍能发现会话并取到近期消息。会话同步用最后保存的游标补消息，服务端固定本轮结束位置，设备用 `next_page_token` 继续翻页。客户端在同一个本地事务里保存每页的变化和 `next_cursor`。推送按消息 ID 去重、按版本更新，收到推送或发出 `PUSH_ACK` 都不推进游标。验收已验证客户端进程在事务提交前被终止后，重启仍能从原游标补齐。

## 最后一条推送丢了

设备已同步到 40，消息 41 已保存，但推送丢了，之后也没有新消息。即使连接一直在线，设备也会到点用原游标发起 `SYNC`，补回 41。真实 TiDB 验收已覆盖这条路径。

设备在前台在线时定期同步账户和可访问的会话，客户端默认每 30 秒检查一次，部署时可调整。推送、ACK 和心跳不延后同步。同一目标若已有同步任务，就等本轮结束后再查。失败时保留游标，按有上限的退避重试，并遵守服务端给出的最短等待时间。

## 断线重连

普通断线后，客户端会重新认证，先同步账户，再用各会话原来的有效游标补消息。收到 `SESSION_REPLACED` 时，旧连接停止自动重连。如果同步分页票据失效，客户端用最后落盘的 `next_cursor` 开新一轮。真实 TiDB 验收已覆盖普通重连、同一设备接管和分页票据到期后的续读。

## 长期未同步后的恢复

增量同步凭证自签发起有效 30 天。凭证到期且历史代次、权限范围一致时，`SYNC` 返回 `CURSOR_EXPIRED`。设备读完整个 `SNAPSHOT` 后，把近期消息、`resume_cursor` 和待补历史范围一起保存。例如上次同步到 200，快照包含 251–350，设备可以继续收 351 以后的消息，同时记下 201–250 待补。重启或再次取快照后仍要保留这段记录。

会话快照最多包含最近 100 条。快照落盘后，客户端继续同步新消息，同时用 `HISTORY` 向前补旧消息。每页历史和剩余待补范围一起保存，历史读取不推进增量游标。历史分页票据失效时，从最后落盘的边界重新请求；遇到空页且还有票据时继续。客户端单独记录低于服务端历史保留下界的范围。首期按只追加的文本计算待补范围，更早的历史也可按需请求。

首次同步或收到 `INVALID_CURSOR` 时，从近期快照建立新的同步进度。权限或历史代次变化时，先隐藏受影响的旧消息并清除旧进度，再为仍有权限的范围取新快照。客户端保留服务端给出的 `data_loss_possible` 提示。

## 怎么验收

| 模拟故障 | 验收结果 |
|---|---|
| 回执丢失，发送设备重启 | 提交前中断可以用原键补发，提交后能查回原回执。消息最多提交一次，后续消息按队列顺序发送 |
| 服务提交后、推送前退出 | 服务重启后，发送端查回回执，接收端同步到同一条消息 |
| 新会话的第一条推送丢失 | 连接保持在线，账户同步发现新会话并补回第一条消息 |
| 已知会话的最后一条推送丢失 | 连接保持在线且没有后续消息时，客户端定时发起同步并补齐 |
| 接收设备断线重连 | 恢复认证后自动同步账户，并用原游标补齐各会话。分页票据到期时从最后保存的同步游标重新开始 |
| 同一设备的新连接接管旧连接 | 旧连接收到 `SESSION_REPLACED` 后停止自动重连 |
| 推送乱序、重复，或设备在保存同步页时退出 | 消息按会话顺序展示且不会重复，推送不推进游标。重启后，消息和游标要么都保留这次更新，要么都回到更新前 |
| 增量同步凭证到期，快照只覆盖近期 | 从近期快照恢复新消息，待补范围在重启和再次取快照后仍在 |
| 历史读取中断、票据到期或低于保留下界 | 从已落盘边界继续补齐，低于下界的部分单独标记 |
| 会话撤权或重新授权 | 撤权后隐藏旧消息并停止旧历史分页，重新授权使用新的访问版本，旧推送无法恢复旧视图 |

客户端验收通过进程内协议帧连接真实 TiDB，运行命令和集中重连测量见[本机控制台与验证](./storage.md#本机控制台与验证)。独立转发、多个实例共用设备身份、跨地域恢复和“已送达”回执各自需要单独定义。
