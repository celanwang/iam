# 网关容量压测

基线为 `main` 的 `d8038e6`。网关使用默认限额，测试客户端经本机 TCP + TLS 1.3 访问网关，消息写入 OrbStack 内的 TiDB、TiKV、PD 8.5.7，各一个实例。宿主机为 Apple M4 Max、macOS 15.5，容器环境为 16 vCPU、约 15.7 GiB 内存。压测使用调试构建，客户端和网关共享一个 8 工作线程的 Tokio 运行时。

## 负载与计时

| 场景 | 发送负载 | 后台负载 |
|---|---|---|
| 纯发送 | 100 或 200 次/秒，短文本 | 接收端离线 |
| 集中重连 | 100 次/秒，短文本 | 8、32 或 64 台设备在测量开始 750 ms 后同时重连。客户端重走 TLS、`AUTH` 和账户同步，并从 SQLite 的旧游标补 24 条会话消息，每页最多 8 条。补齐使用另一个会话，和发送共用同一网关与 TiDB |
| 正常读对照 | 70 次/秒，64 KiB 文本 | 两个已认证设备持续读取推送 |
| 慢读背压 | 70 次/秒，64 KiB 文本 | 一台设备继续读，另一台的 TCP 接收缓冲请求设为 4 KiB，认证后停读 7 秒，再读取剩余推送 |

每组使用独立测试库和四条已预热的发送连接，各连接最多一个在途请求。发送端在 6 秒内按固定时间表发起请求。到达时四条连接都忙则记为未发出，请求不排到下一时隙。发出的请求按已提交、拒绝、超时和其他失败分类。发送 RTT 从客户端开始构造该次发送请求计到收到并校验回执。另记从计划到达计时的延迟，其中包含发送侧调度滞后。

集中重连记录 TCP + TLS 成功耗时、`AUTH` 成功耗时、握手失败、认证及同步入口拒绝次数。补齐从计划放行重连计到观察到 SQLite 游标落盘，包含客户端本地调度、打开数据库、重试和最多约一个 5 ms 观察周期的误差。测试检查每台设备的消息序号连续且无重复。慢读场景验证邻居连接继续收推、慢连接限时关闭，并在负载结束后从停读前落盘的游标补齐全部消息。

## 实测结果

连续运行两轮，表中按第一轮 / 第二轮列出结果。所有实际发出的前台 `SEND` 都已提交，拒绝、超时和其他失败均为零。

| 场景 | 每轮计划发送 | 已提交 | 未发出 | 发送 RTT P50 / P99（ms，两轮） | 从计划到达计时的 P99（ms） |
|---|---:|---:|---:|---|---:|
| 纯发送 100 次/秒 | 600 | 600 / 600 | 0 / 0 | 6.20 / 20.92 · 5.84 / 12.71 | 21.87 / 13.85 |
| 纯发送 200 次/秒 | 1,200 | 952 / 908 | 248 / 292 | 21.70 / 39.78 · 22.38 / 60.96 | 40.42 / 61.97 |
| 8 台设备集中重连 | 600 | 599 / 597 | 1 / 3 | 6.14 / 25.67 · 6.74 / 25.14 | 25.95 / 26.29 |
| 32 台设备集中重连 | 600 | 600 / 600 | 0 / 0 | 6.05 / 19.99 · 6.77 / 17.54 | 22.55 / 18.16 |
| 64 台设备集中重连 | 600 | 596 / 600 | 4 / 0 | 6.42 / 49.74 · 6.85 / 31.42 | 51.07 / 32.63 |
| 正常读对照 | 420 | 420 / 420 | 0 / 0 | 8.63 / 21.58 · 8.27 / 20.37 | 25.63 / 23.08 |
| 慢读背压 | 420 | 420 / 420 | 0 / 0 | 8.69 / 21.14 · 8.65 / 20.01 | 22.36 / 21.24 |

| 集中重连 | 每轮补齐设备 | TCP + TLS 成功耗时 P99（ms） | 认证成功耗时 P99（ms） | 认证 / 同步入口拒绝（两轮） | 补齐 P50（ms） | 最后一台补齐（ms） |
|---|---:|---:|---:|---|---:|---:|
| 8 台 | 8 | 4.32 / 5.25 | 13.19 / 10.87 | 0 / 0 · 0 / 0 | 93.36 / 105.54 | 101.28 / 107.53 |
| 32 台 | 32 | 19.81 / 17.33 | 28.42 / 18.80 | 0 / 16 · 0 / 16 | 171.44 / 132.09 | 448.69 / 433.79 |
| 64 台 | 64 | 31.72 / 20.90 | 61.96 / 45.02 | 31 / 50 · 29 / 53 | 522.25 / 474.97 | 1,390.92 / 1,283.32 |

两轮握手失败均为零。64 台设备有 95 / 93 次成功握手，其中 31 / 29 次认证被入口拒绝后重连。该档发送 P99 升至 49.74 / 31.42 ms。只看重连到最后一台补齐的窗口，发送 P99 为 58.81 / 36.05 ms，分别有 136 / 129 个已提交样本。认证和同步入口已有可观测的拒绝，存储与网关排队各自占多少时间还需要分段计时。

慢读组两轮中，正常设备均收齐 420 条推送。停读设备各读到 6 条完整推送后观察到连接关闭，并从旧游标补齐 420 条，补齐耗时为 4.03 / 4.04 秒。正常读组两台设备均收齐 420 条。两组发送 P99 接近，样本仅覆盖单个慢连接与 64 KiB 消息的同一负载。

100 次/秒的纯发送两轮承接了全部计划请求。200 次/秒档有约 21% / 24% 的请求因四条客户端发送连接均忙而未发出，测试时段分别提交约 159 / 151 次/秒。这个结果量化了当前客户端并行度下的吞吐，网关总连接上限和独立压测机下的饱和点仍待测量。

## 复现

使用空闲的本机 TiDB，单独运行该测试。

```sh
IAM_TIDB_TEST_URL='mysql://root@127.0.0.1:4000/iam_test' \
IAM_TIDB_ALLOW_TEST_WRITES=1 \
cargo test --locked -p iam-gateway --test tls capacity::tidb_tls_gateway_capacity -- --exact --ignored --nocapture
```

每组打印请求数、P50/P95/P99、重连重试和补齐耗时。该测试用于对比同环境下的负载变化，生产容量与同地域服务端 P99 目标需要在独立压测机和部署拓扑上测量。

## 集中重连分段测量

以 `7131da9` 的入口策略为基线，前后各测两轮，沿用上面的 TCP + TLS、TiDB 和 SQLite 拓扑。每轮测纯发送、32 台和 64 台设备集中重连。前台按每秒 100 次计划发送 600 条。两版都开启 `profile` 编译特性，采集网关派发、发布锁、响应队列和 TLS 写出，以及 TiDB 时钟合批等待、取连接并开启事务、控制行 SQL、发送事务和同步读事务。

下表为 64 台设备场景，各列列出两轮 P99，单位 ms。时钟事务包含取连接、控制行 SQL 和提交，控制行 SQL 包含锁等待与 SQL 往返。多个请求共享一笔时钟事务，表中按请求记录它所等待的事务，分位数无需相加。客户端 `AUTH` RTT 计入网关入场等待，服务耗时从进入消息服务开始。

| 阶段 | 立即拒绝 | 最多等待 75 ms |
|---|---:|---:|
| 服务端 TLS 握手 | 28.69 / 25.87 | 21.25 / 27.92 |
| 客户端 `AUTH` RTT | 47.14 / 50.42 | 41.06 / 56.07 |
| `AUTH` 入场等待 | 立即通过或拒绝 | 15.89 / 19.37 |
| `AUTH` 时钟合批等待 | 22.76 / 25.56 | 22.68 / 36.59 |
| `AUTH` TiDB 时钟事务 | 30.33 / 26.73 | 22.88 / 36.68 |
| `SYNC` 入场等待 | 立即通过或拒绝 | 24.78 / 32.61 |
| `SYNC` 服务耗时 | 33.32 / 49.66 | 32.41 / 33.30 |
| `SYNC` 时钟合批等待 | 11.20 / 20.10 | 11.04 / 12.58 |
| `SYNC` TiDB 时钟事务 | 15.35 / 32.03 | 14.15 / 14.25 |
| `SYNC` TiDB 读事务 | 10.61 / 12.38 | 10.71 / 9.71 |
| `SEND` 网关派发排队 | 0.04 / 0.06 | 0.06 / 0.04 |
| `SEND` 网关响应排队 | 0.16 / 0.21 | 0.19 / 0.10 |
| `SEND` TiDB 控制行 SQL | 15.31 / 20.46 | 12.32 / 13.03 |
| `SEND` TiDB 提交事务 | 23.37 / 30.39 | 25.66 / 20.30 |

基线中 `SEND` 控制行 SQL 的 P99 从纯发送的 0.60–5.34 ms 上升到 15.31–20.46 ms。网关派发和回包排队远短于存储时间。入口拒绝还会触发客户端退避，默认首次至少 250 ms。最终改动为新认证和增量同步增加有界等待，各档在途配额保持原值。测试将同步并发从 16 降到 8 后，64 台场景有 55 次同步拒绝，最后一台约 1.09 秒补齐，因此保留 16。

| 场景 | 发送 P99（ms），立即拒绝 → 有界等待 | 最后一台落盘（ms），立即拒绝 → 有界等待 |
|---|---|---|
| 纯发送 | 8.64 / 14.22 → 14.99 / 24.62 | — |
| 32 台重连 | 18.68 / 19.36 → 38.02 / 17.03 | 442.21 / 450.77 → 386.80 / 256.67 |
| 64 台重连 | 23.63 / 30.64 → 25.88 / 20.48 | 1,063.55 / 1,363.14 → 531.93 / 550.66 |

64 台场景的认证拒绝从 25 / 31 降至零，同步拒绝从 53 / 50 降到 32 / 32。前台发送均没有协议拒绝或超时。最终两轮 64 台均发出全部 600 条，纯发送第二轮及 32 台第一轮分别有 8 条和 1 条因客户端发送连接忙而未发出。末台补齐耗时在两轮均下降，发送 P99 仍受本机存储波动影响。32 台有一轮升至 38.02 ms，64 台最差一轮从 30.64 降到 25.88 ms。

另用默认构建复跑完整容量套件。64 台在 548.04 ms 内全部补齐，发送 P99 为 22.51 ms。慢读组实际提交 410 条，正常设备收齐推送，慢读设备收到 6 条后关闭并在 4.02 秒内从旧游标补齐。慢读组发送 P99 为 59.45 ms，正常读对照为 62.52 ms。完整套件中 8 台、32 台两组的发送 P99 分别出现 73.64、72.73 ms，说明短测仍存在长尾波动。

```sh

IAM_TIDB_ALLOW_TEST_WRITES=1 \
cargo test --locked -p iam-gateway --features profile --test tls \
  capacity::tidb_tls_gateway_reconnect_profile -- --exact --ignored --nocapture
```

## 时钟合批窗口对照

以 `e700682` 为基线，沿用网关的 75 ms 入场等待、原有发送事务和压测负载。在同一真实 TCP + TLS 和 TiDB 环境下，分别用 1、2、4 ms 的时钟收集窗口测试纯发送、32 台和 64 台重连。每个场景做三轮，轮换窗口先后顺序，共 27 组。每组独立建库，测量前结束建连和预热。

`clock_committed` 在时钟后台任务确认 TiDB 提交时增一，一笔事务只记一次。`clock_requests` 是成功取得该批次采样结果的请求数。时钟提交数覆盖 `AUTH`、`RECONNECT`、`SYNC` 共用的采样器。纯发送仍在各自的发送事务内采样，因此合批时钟事务数应为零。发送 P99 使用客户端实际发出并取得提交回执的请求，另外记录未发出数量。补齐时间从重连放行计到最后一台设备的游标和消息落盘。

表中每格按第一、第二、第三轮顺序记录。各组计划发送 600 次。全部发出的请求均取得提交回执，所有重连设备均补齐并通过消息连续性检查。各组时钟事务尝试数与确认提交数相同。

| 重连设备数 | 窗口（ms） | 合批时钟事务数 | 发送 P99（ms） | 最后一台落盘（ms） | 未发出 |
|---|---:|---:|---:|---:|---:|
| 0 | 1 | 0 / 0 / 0 | 10.64 / 9.15 / 23.34 | — | 0 / 0 / 1 |
| 0 | 2 | 0 / 0 / 0 | 62.50 / 10.34 / 15.83 | — | 16 / 0 / 0 |
| 0 | 4 | 0 / 0 / 0 | 105.43 / 13.24 / 11.10 | — | 57 / 0 / 0 |
| 32 | 1 | 18 / 18 / 30 | 21.47 / 30.50 / 202.06 | 228.87 / 233.88 / 591.20 | 0 / 0 / 147 |
| 32 | 2 | 19 / 18 / 20 | 23.90 / 17.46 / 68.04 | 239.87 / 254.36 / 283.83 | 0 / 0 / 18 |
| 32 | 4 | 19 / 19 / 18 | 23.35 / 17.05 / 203.55 | 244.61 / 227.42 / 322.86 | 1 / 0 / 105 |
| 64 | 1 | 41 / 43 / 40 | 31.64 / 20.90 / 24.53 | 543.33 / 538.86 / 550.84 | 1 / 0 / 0 |
| 64 | 2 | 40 / 39 / 38 | 30.02 / 27.60 / 27.17 | 549.01 / 554.45 / 576.41 | 0 / 0 / 0 |
| 64 | 4 | 55 / 39 / 37 | 62.20 / 24.89 / 31.21 | 1,252.53 / 545.00 / 535.35 | 11 / 0 / 1 |

保留 **1 ms**。64 台重连时，2 ms 三轮都减少了时钟事务，合计从 124 笔降到 117 笔，约减少 5.6%。但三轮发送 P99 的中位数从 24.53 升到 27.60 ms，最后落盘中位数从 543.33 升到 554.45 ms。4 ms 在首轮增加了时钟事务，补齐耗时达到 1.25 秒。32 台的时钟事务中位数为 18、19、19。该负载的第三轮发送 P99 波动较大，纯发送也出现了长尾。选择窗口时保留这些样本，并同时比较提交量和未发出数量。

1、2、4 ms 分别复验了 TiDB 时钟回拨、增量同步与分页票据到期、恢复票据到期、时钟批次提交响应丢失和未决发送跨关窗。分页票据在等于到期时间时返回 `PAGE_TOKEN_EXPIRED`，客户端可从最后保存的游标继续。旧发送持锁时，时钟批次和状态查询等待结算。

```sh
export IAM_TIDB_TEST_URL='mysql://root@127.0.0.1:4000/iam_test'
export IAM_TIDB_ALLOW_TEST_WRITES=1
cargo test --locked -p iam-gateway --features profile --test tls \
  capacity::tidb_tls_gateway_clock_windows -- --exact --ignored --nocapture

for window in 1 2 4; do
  IAM_TIDB_TEST_CLOCK_WINDOW_MS="$window" \
    cargo test --locked -p iam-store --features profile --test durability \
    tidb_clock_batch_ -- --ignored --test-threads=1
  IAM_TIDB_TEST_CLOCK_WINDOW_MS="$window" \
    cargo test --locked -p iam-store --features profile --test durability \
    tidb_protocol_preserves_the_close_watermark_during_clock_rollback -- --exact --ignored
done
```
