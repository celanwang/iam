# TiDB 控制行与重连压测

基线是 `main` 的 `6a52372`。使用 OrbStack 内的 TiDB、TiKV、PD v8.5.7，各一个实例，容器环境为 16 vCPU、约 15.7 GiB 内存。测试走真实协议处理器和 TiDB，重连用实际的 `iam-client` 与 SQLite。该测量不包含外部网络、网关或 TLS。

## 测量方法

| 场景 | 每波额外负载 |
|---|---|
| 纯发送 | 无 |
| 并发认证 | 4 个设备各连续完成 4 次 `AUTH` |
| 空同步 | 4 个已认证设备各用有效游标完成 4 次空会话 `SYNC` |
| 集中重连 | 4 个设备同时重新认证，各同步 1 页账户变化和 3 页会话消息，每页 8 条，共补 24 条 |

四组均使用同一个发送设备。每波同时放行发送端和后台设备，发送端连续提交 3 条短文本；所有任务结束后再开始下一波。每组预热 8 波，测量 160 波，共 480 次 `SEND`。发送会话与补齐会话分开，后台实例各用独立的连接池。重连前从同一个已持久化的客户端基线恢复，连接池预热和本地库复制均在开始计时前完成。每次重连都校验 SQLite 中已有完整且有序的 24 条消息。这个闭环负载用于比较争用，不能换算为生产容量。

- **请求**从进入 `TidbService::handle_frame` 到返回协议结果。
- **事务**包含取连接、开始事务、业务 SQL 和提交响应。`SEND` 额外记录扣除控制行 SQL 后的剩余事务时间。同步分别记录时钟事务和读取事务。
- **控制行 SQL**测量 `SELECT … FOR UPDATE` 的完整往返，包含读键和排队。TiDB 的 [DATA_LOCK_WAITS](https://docs.pingcap.com/tidb/stable/information-schema-data-lock-waits/) 每 20 ms 抽样确认等待键，过滤到本轮库的 `store_control` 主键 1。短等待可能不在抽样窗口内。
- **TiKV 排队等待**取单节点 waiter lifetime 直方图在本组前后的差值。该指标没有键标签，用锁视图交叉核对归因。分位数使用桶的上界，样本数是等待次数。
- **补齐时间**从客户端开始重连，到末页消息及游标写入 SQLite 后重新等待入站帧。前三组没有重连或漏收回放，因此没有补齐时间。

独立连续运行两轮。每格的两个值分别对应第一轮和第二轮，延迟单位为 ms。

|---|---:|---:|---:|---:|---:|---:|
| 纯发送 | 6.01 / 5.84 | 11.37 / 14.24 | 11.31 / 14.20 | 0.48 / 0.50 | 1.12 / 5.88 | 5.45 / 5.27 |
| 并发认证 | 12.58 / 17.16 | 25.98 / 110.75 | 25.92 / 110.63 | 7.26 / 10.35 | 19.79 / 103.99 | 5.28 / 6.01 |

| 集中重连 | 12.38 / 12.92 | 45.34 / 58.48 | 45.28 / 58.45 | 7.41 / 7.85 | 32.41 / 38.18 | 5.23 / 5.43 |

| 场景 | TiKV 排队次数 | TiKV 单次等待均值（ms） | 等待 P99 桶上界（ms） | 抽到控制行等待的次数 / 总抽样数 |
|---|---:|---:|---:|---|
| 纯发送 | 0 / 0 | — | — | 0/158；0/167 |

并发场景中，同一控制行最多同时有 4 个等待者。除第一轮并发认证中有一次抽样包含其他或无法归属的键外，抽到的等待都指向本轮库的控制行。

| 后台负载 | 时钟事务 P50 / P99（第一轮） | 时钟事务 P50 / P99（第二轮） | 读取事务 P50 / P99（第一轮） | 读取事务 P50 / P99（第二轮） |

集中重连每轮测得 640 次补齐。24 条消息全部落盘的时间，第一轮 P50 / P95 / P99 为 **73.53 / 128.46 / 175.59 ms**，第二轮为 **82.77 / 158.74 / 277.10 ms**。

## 瓶颈定位

控制行争用是本机发送延迟增加的主要来源。纯发送的取锁 SQL P50 约 0.5 ms，并发时升至 7–10 ms，而扣除这条 SQL 后的发送事务 P50 仍约 5–6 ms。空同步不返回消息也产生了大量锁等待，其时钟事务 P50 约 12.5 ms，实际读取事务约 2 ms。两轮都出现这个差距，说明应先研究时钟事务与控制行争用，再判断是否需要优化消息范围读取。

并发认证的尾延迟两轮差异明显，不能据此断定三种后台负载的最坏情况排序。结果只覆盖本机四设备的同步波次和 24 条积压。事务边界、时钟回拨保护和关闭水位的正确性约束仍以现有存储设计为准。

## 复现

以下命令在合批分支上会用同一服务实例依次运行关闭和开启合批的对照组。原基线的四个后台实例独立开连接池，数据留作历史记录。

使用空闲的专用本机 TiDB 集群，单独运行该测试。`DATA_LOCK_WAITS` 查询需要 `PROCESS` 权限。配置下列 TiKV 容器名可读取真实排队时间；省略时仍会记录控制行 SQL 和等待键抽样。

```sh
IAM_TIDB_TEST_URL='mysql://root@127.0.0.1:4000/iam_test' \
IAM_TIDB_ALLOW_TEST_WRITES=1 \
IAM_TIDB_PERF_TIKV_CONTAINER=iam-tidb-tikv-1 \
cargo test --locked -p iam-store --lib store::perf::profile_sync_contention -- --exact --ignored --nocapture
```

测试只在 `iam_test_*` 隔离库运行。计时点仅编译进测试，生产路径的 SQL、事务边界和处理顺序保持不变。

## 时钟采样合批对照

使用本机 TiDB v8.5.7，保留四组原有负载和样本量。发送端和四个后台设备通过同一个服务实例处理请求。关闭和开启合批使用相同拓扑，每组各测两次。下表每格按「关闭 → 开启」记录。

| 场景 | `SEND` P99 第一轮（ms） | `SEND` P99 第二轮（ms） | 时钟事务次数，两轮 | TiKV 排队次数，两轮 |
|---|---:|---:|---|---|
| 纯发送 | 11.40 → 8.45 | 8.18 → 7.37 | 0 → 0；0 → 0 | 0 → 0；0 → 0 |
| 并发认证 | 29.69 → 15.80 | 17.49 → 10.94 | 2,560 → 645；2,560 → 640 | 2,880 → 800；2,880 → 800 |
| 空 `SYNC` | 30.64 → 15.74 | 17.47 → 12.19 | 2,560 → 668；2,560 → 693 | 2,880 → 794；2,880 → 797 |
| 集中重连 | 38.61 → 16.10 | 262.33 → 9.50 | 3,200 → 1,119；3,200 → 864 | 3,342 → 746；3,406 → 728 |

纯发送不经过合批，差异是测量波动。第二轮关闭合批的重连组有明显长尾，`SEND` P95 为 30.70 ms，P99 为 262.33 ms。判断收益时同时看两轮的中位数、事务次数和等待次数。

- 并发认证平均每批 3.97 / 4.00 个请求，排队到封批 P50 为 1.56 / 1.45 ms。时钟事务 P50 为 11.38 → 5.54 / 12.16 → 5.71 ms。
- 空同步平均每批 3.83 / 3.69 个请求，排队到封批 P50 为 1.47 / 1.48 ms。时钟事务 P50 为 11.38 → 4.76 / 11.47 → 4.77 ms。
- 集中重连平均每批 2.86 / 3.70 个请求。每个设备补齐 24 条消息并落盘的 P50 为 61.54 → 47.25 / 61.48 → 46.31 ms，P99 为 181.12 → 113.28 / 393.68 → 64.38 ms。

这里的集中重连走当前客户端默认的 `AUTH` 加账户和会话 `SYNC`。协议 `RECONNECT` 另有故障验收。合批的收益来自减少同一实例的锁请求，实例之间仍通过同一控制行协调。
